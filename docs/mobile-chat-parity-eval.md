# 移动端对话窗口功能对齐桌面端——评估文档

> 状态：评估稿（未实施，2026-10-26 第二版：按「移动端提供上下文、runtime 留桌面」定位重构）。基于桌面端 thread card + 独立会话页的全量功能盘点。
> 关联：`docs/mobile-agent-plan.md` §13-§18（云同步方案 A 与 thread card 跨端互认，已全部落地）。

## 0. 产品定位：双端分工模型

**移动端对话窗不是桌面的复制品，定位是三件事：**

1. **上下文提供方**——把「正在看的笔记/现场想法」喂进对话（笔记上下文注入是移动端对话窗的核心价值，而非锦上添花）；
2. **会话随身查看器**——桌面 runtime 会话的富内容（markdown/代码/工具过程）在手机上完整可读，随时随地跟进桌面 agent 的执行过程与结论；
3. **轻量续聊**——简单追问用内置 openai_compatible 引擎直答，不追求桌面 runtime 的工具能力。

**依赖 runtime 的功能保留在桌面端执行**：斜杠命令/skill、模型与权限设置、工具调用、fork、后台终端、审批队列、排队消息等——它们是「桌面工作台」能力，移动端不复制执行环境，只消费其结果（已上云的线程数据）。

由此，功能对齐分三类：

1. **通用类（云端线程数据即可支撑）**——移动端缺失但应补齐：消息 Markdown 渲染、代码块、工具调用展示、消息复制、时间戳、草稿、会话管理等。**对「查看器」定位而言这些是刚需**（桌面 runtime 回复里满是代码/工具过程，手机读不懂就失去查看价值）。约占桌面功能面一半以上。
2. **上下文与轻量引擎增强（chat.rs 小改）**——笔记上下文注入是核心项；图片输入 vision 按需。
3. **桌面 runtime 执行类（不在移动端复刻）**——按分工设计保留在桌面；手机侧只做两件相关事：a) 桌面卡只读查看（§17 已落地）；b) 可选的「委托桌面执行」通道（见 §4，远期）。

**建议路线**：P0 渲染层（查看器刚需）→ P1a 上下文注入（移动端核心价值，升级优先级）→ P1b 会话管理补齐 → P2 图片输入按需。「委托桌面 runtime 执行」作为远期可选路线单独评估。

## 2. 分层方案

### P0：消息渲染对齐（纯前端，规模：中）

**目标**：消除「桌面回复很丰富、手机一团纯文本」的主要观感差距。改 `ChatScreen.tsx` + `agent-thread-card.tsx` 共用的消息渲染组件（抽 `MessageBubble` 为共享渲染器）。

- **Markdown 渲染**：复用根依赖已有的 `marked`（v17，与 @tiptap/markdown 同源，零新增依赖）。桌面渲染管线（`agent-thread-card-markdown.ts` 的 marked 配置 + 转义白名单 + CJK 加粗修正）约 300 行可移植；移动端输出到 `element.innerHTML` 前需同等转义策略（桌面只放行 `<a>`）。
- **代码块**：`<pre><code>` + 语言标签 + 长按/点击复制；高亮用 highlight.js 核心按需注册常用 10 语言（~60KB）或首版纯样式不高亮（成本最低，观感 80 分）。
- **工具调用行**：图标 + 工具名 + 命令型单行预览 + 点击展开 toolInput/toolData（数据已上云，纯渲染）。
- **消息操作**：复制按钮（打勾反馈）。
- **时间戳**：气泡底部相对时间。
- **流式**：liveText 阶段按 markdown 渲染（每帧 parse 移动端可接受），stream_end 落库版替换。

风险：marked 渲染 XSS 面与桌面同构（转义白名单移植要完整）；bundle +~80KB。

### P1a：笔记上下文注入（chat.rs 小改，规模：小，**移动端对话窗的核心能力**）

`agent_chat_send` 加可选参数 `{ noteContext?: { notebookId, relativePath } }`；chat.rs 首条消息时读笔记文件，按桌面同款 `[CONTEXT]` 块（任务标签 + 笔记内容前 500 字）拼接进发送 prompt，**落库 content 仍存用户原文**（与桌面 content/llmContent 分离语义一致）。卡片发送时自动带当前笔记；ChatScreen 新建对话可选携带（入口：从笔记页「就此笔记提问」）。

这是定位①（上下文提供方）的落地：手机上「正在看的笔记 + 一句话」，桌面/云端引擎拿到完整语境。

### P1b：会话与交互补齐（纯前端，规模：中）

- 草稿持久化（卡片 attrs.inputDraft 已互认 + ChatScreen localStorage）。
- 会话列表增强：日期分组、类型筛选（mobile/云端移动端会话已有类型）、未读点、长按菜单（重命名/删除）；**收藏/归档**需 threads payload 加字段（v1 JSON 版本化向后兼容，旧端忽略新字段，无迁移成本）。
- 超长消息折叠、滚动跟随/脱离、顶部历史分页。
- 卡片「全屏打开」：卡片 header 加按钮跳 ChatScreen（threadId 直通，移动端导航已有）。
- 连续工具分组、桌面卡特殊消息类型徽章（context-compaction 等，桌面卡消息移动端只读展示时更完整）。

### P2：可选增强（按需排期）

- **P2a 图片输入（中）**：`V2ThreadMessage` 加 `attachments` 字段（JSON，向后兼容）；chat.rs 请求体按 openai_compatible vision 格式（`image_url` data URL）发送；composer 接 `attachment_save`（已有基建）选图。渲染：气泡下缩略图（`attachment_read` 读回）。
- **P2b 其他**：KaTeX 懒加载、生成图片条、turn 时长记录。

### 保留在桌面端执行（按分工设计，不在移动端复刻）

斜杠命令与 skill 菜单、Model/Mode/Permission/Workspace 设置、工具调用的**执行**、排队消息与转向、fork、后台终端与 job 面板、Codex 审批队列、会话导出、脱敏发送、@文件夹引用与 NotePicker（可做远期简版：基于现有 `search` 命令的笔记引用）、拖拽/焦点隔离（桌面嵌入形态专属）。

移动端对以上能力的正确消费方式：
- 工具调用**结果**已在云端线程 → 移动端只读渲染（P0 工具行）；
- 复杂操作 → 回桌面完成（手机上看到的会话与桌面完全同源）。

## 3. 关键技术决策点

### 3.1 高亮与公式库的体积权衡
移动端 bundle 现 ~738KB（gzip 233KB）。Shiki 全量不可行；KaTeX ~300KB+字体。建议：首版代码块不高亮（纯样式+语言标签+复制），验证观感后再决定 highlight.js 按需注册；KaTeX 列 P2b 懒加载（动态 import，用到才拉）。

### 3.2 上下文注入的参数面
chat_send 现签名 `(thread_id, content)`。加第 4 参数后注意：桌面读移动端线程时，消息 content 为原文（无上下文块），与桌面语义一致；llmContent 不上云、不落库，只在请求瞬间拼接（重启/换端无损）。上下文长度截断对齐桌面（当前笔记内容前 500 字 + 任务标签）。

### 3.3 图片输入的消息模型
`V2ThreadMessage`（flowix-sync + flowix-mobile 两处结构）加 optional `attachments: Vec<V2ThreadAttachment>`；thread payload JSON 版本化已具备向后兼容（旧端 serde 忽略未知字段）。图片本体建议先走 **data URL 内嵌消息**（简单，受消息体积影响）或复用笔记附件通道存 blob 引用（更优，改动多）——首版内嵌、限单图 1MB。

### 3.4 收藏/归档字段
threads payload（title/messages 之外）或本地表。**上云**才能双端一致（桌面收藏移动端可见），建议 payload 顶层加 `favorite/archived` 可选字段。

## 4. 建议实施顺序

1. **P0 渲染层**（共享 MessageBubble 渲染器：markdown/代码块/工具行/复制/时间戳）——查看器刚需、零引擎改动、一次交付。✅ **2026-10-26 已交付并实机验证**（见 mobile-agent-plan.md §19）。
2. **P1a 上下文注入**（chat.rs 小改）——移动端对话窗的核心价值，让「手机提供上下文」名副其实。✅ **2026-10-26 已交付并实机验证**（见 mobile-agent-plan.md §19）。
3. **P1b 会话管理**（列表分组/重命名/收藏/未读 + 草稿 + 卡片全屏跳转）。
4. **P2 图片输入**（schema + vision）按需求热度排期。
5. **远期可选**：委托桌面 runtime 执行（§6）。

每步独立可交付、独立可验证（模拟器 CDP 链路已全通，验证成本低）。

## 5. 跨端协作边界（当前已具备）

分工模型下，现有链路已天然覆盖三类跨端场景，无需新增能力：

| 场景 | 链路 | 状态 |
|---|---|---|
| 手机看桌面 runtime 会话 | 桌面 runtime 写线程 → 云同步 → 手机 threads 拉取 + 只读渲染 | ✅ 已通（§17/§18）；P0 渲染层补齐「看得懂」 |
| 手机轻量追问（内置引擎） | chat_send → openai_compatible 直答 → 上云 → 桌面可见 | ✅ 已通（方案 A4） |
| 手机给对话喂笔记上下文 | P1a 落地后，卡片消息自动携带当前笔记 | 待 P1a |

注意一个语义边界：**移动端内置引擎续聊桌面 runtime 发起的线程**时，后续回复由轻量引擎生成（无工具执行），历史中桌面 runtime 的工具消息仍在。这符合分工模型（手机只做简单追问），但 UI 上建议在输入框 placeholder 或会话 meta 标注当前引擎身份（P1b 顺带），避免用户误以为手机也能跑工具。

## 6. 远期可选路线：委托桌面 runtime 执行

「手机发起、桌面执行」的完整形态——手机对话窗发送消息时可选目标 runtime（如 deepseek-harness），实际执行在桌面端，手机只收结果。评估如下：

**技术路径（消息通道方案）**：
1. 手机发消息带 `runtimeRequest` 标记（消息 schema 加可选字段，向后兼容）；
2. 云端线程更新 → 桌面 threads-changed 监听发现待执行请求（现有通道，10s 轮询级延迟）；
3. 桌面侧新增「移动端请求队列」处理：按标记路由到对应 runtime，执行、结果消息上云；
4. 手机拉取渲染（P0 能力）。

**依赖与成本**：
- 依赖桌面进程在线（离线则请求滞留，需超时/回落策略：桌面不在线时手机内置引擎直答并注明）；
- 桌面端为新功能（请求队列 + runtime 路由 + 权限确认 UI——远程触发的工具执行涉及权限模型，至少要桌面侧确认开关）；
- 延迟受云同步轮询限制（现状 ~10s 起步；未来 SSE/推送改造后可降）。

**评估结论**：技术上可行、无硬阻塞，但属于「跨端远程执行」新能力而非功能对齐，涉及桌面权限模型与在线假设，**列为远期独立立项**，不进本轮对齐范围。当前分工模型下，手机轻量追问 + 回桌面做复杂操作的体验已闭环。
